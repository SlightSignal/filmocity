# Windows verification matrix for the testing LLM

The current reviewed environment is standard, GIL-enabled CPython 3.13.16 Windows x64. See [release readiness](RELEASE_READINESS.md) for exact RC6 scoped Windows results and the [build guide](../packaging/README.md) for current locks. This broader historical matrix remains separate qualification work; its rows are not automatically marked passed by finite RC6 acceptance. Older Python minimum/reparse cases below are historical or separate portability scenarios.

Use this matrix with [WINDOWS-TEST-HANDOFF.md](WINDOWS-TEST-HANDOFF.md), which contains source verification, build commands, candidate identity, export history and native shutdown procedures. Test Windows x64 first. The source ZIP is a development handoff; it is not a Windows executable or a claim of Premiere/Resolve parity.

## Execution contract

1. Verify the handoff manifest, run focused regressions and build a new candidate using the handoff instructions. Preserve the ZIP, build receipt, encoder matrix and executable SHA-256. Record failures before fixing them. Run candidate checks against its captured `inputs`, not a subsequently edited source checkout.
2. Use disposable data and media. Never replace an existing library, receipt, report or output. For failure injection, copy the disposable case first. Record every intercepted request, synthetic response, mocked dependency or intentional corruption; it cannot substitute for an ordinary native pass.
3. Record **PASS**, **FAIL**, **NOT RUN**, or **UNAVAILABLE** per case and per launch mode. PASS requires observed expected behavior and an evidence path. UNAVAILABLE names the missing hardware/dependency. A missing advertised baseline feature is a defect even when the immediate cause is an unavailable dependency. For a claim of full matrix qualification, each in-scope P0 requires a recorded pass; an unrun row remains unverified. Finite RC6 local acceptance and tools-only source publication have the narrower scope documented in release readiness. A source/browser pass does not establish a native WebView2 pass.
4. For a defect, save steps, expected/actual behavior, project before/after, logs, output hashes and a screenshot/video when useful. Assign severity: S0 data loss/wrong-project mutation; S1 crash, unusable editing or wrong export; S2 workflow/accessibility/performance failure; S3 cosmetic. Preserve failing evidence, fix in development source, rebuild, and rerun affected cases plus all P0 smoke cases. Keep results for different hashes separate.
5. Do not install drivers, change system security settings, or fill a system drive for a fault test. Simulate disk-full and sharing errors in an isolated test harness or small disposable volume and identify the method. Kill only processes whose launch/workspace identity was established for this test.

Capture Windows build, CPU, RAM, GPU/driver, storage type/free space, display size/scaling, audio device, WebView2, Python, Node, package versions, FFmpeg/FFprobe hashes/configuration, native/browser launch mode, candidate ID/source hash/executable hash, data path, model/version and power mode. Record a clean Windows account without Python/Node/build tools on PATH separately.

## Create repeatable test material

After the existing handoff has established `$python` and `$candidate`, use its exact media tools. These commands do not launch Filmocity or write to a library:

```powershell
$qa = Join-Path $env:TEMP ("Filmocity QA " + [guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $qa | Out-Null
$inputs = Join-Path $candidate 'inputs'
$tools = Join-Path $inputs 'bin'
$fixtures = Join-Path $qa "Émile's fixtures"
& $python "$inputs\tests\create_acceptance_media.py" --ffmpeg-dir $tools --output $fixtures --h264 --long-minutes 120
if ($LASTEXITCODE -ne 0) { throw 'Fixture generation failed; preserve its receipt' }
```

The new directory contains nine files plus `fixture-manifest.json`: red and blue 6-second, 640×360, 30 fps clips with identical basenames in different Unicode folders; a numbered moving seek/sync clip with six known color regions; stereo beeps; a 50 Hz hum/1 kHz cleanup tone; a half-transparent PNG; Unicode SRT; a 12-second reference project; and a two-hour project reusing the same short media. The latter has 1,200 clips and 14,400 synthetic words. The manifest records exact tools, media hashes, probe output and expected values. Omit `--h264` for FFV1/PCM Matroska fixtures; this does not establish H.264 decoding or encoding support.

Generate the kit **on Windows at its final path**: project media paths are absolute. To seed the disposable library, keep Filmocity stopped and create a NEW data directory:

```powershell
$data = Join-Path $qa 'Native data'
New-Item -ItemType Directory -Path "$data\projects\qa-reference", "$data\projects\qa-long" | Out-Null
Copy-Item -LiteralPath "$fixtures\reference-project.json" -Destination "$data\projects\qa-reference\project.json"
Copy-Item -LiteralPath "$fixtures\long-project.json" -Destination "$data\projects\qa-long\project.json"
$exe = Join-Path $candidate 'artifact\Filmocity.exe'
& $exe --data $data
```

Use the project browser to open the seeded reference/long project. This seeding tests a known document; it does **not** pass the media import case. Import the fixture clips separately into a fresh project for that case. Retain an untouched fixture copy, and make separate project copies for editing, color, captions, faults and performance.

Synthetic transcripts exercise editing only. For actual recognition, record 30–90 seconds of clear human speech with pauses, a repeated sentence and proper names; preserve permission to use that recording and a verbatim reference. Suggested start: “This is the Filmocity editing check. Keep the first sentence. Remove this middle sentence. Émile and O’Neill are reviewing the final cut.” Add a visibly spoken clap for sync and a quiet room-tone section. Record the model, download/cache behavior, elapsed time, incorrect words and timing errors. Do not run speech recognition on the beeps and call it an accuracy test.

Example output check after EX01 (set `$export` to the completed job's actual output file):

```powershell
$export = 'C:\replace-with-actual-job-output\story.mp4'
& $python "$inputs\tests\inspect_acceptance_output.py" --ffmpeg-dir $tools --input $export --output "$qa\EX01-output.json" --width 640 --height 360 --fps 30 --duration 1.5 --expect-audio --color '0.25:255,0,0' --color '1:0,0,255' --full-decode
if ($LASTEXITCODE -ne 0) { throw 'Output check failed; inspect retained JSON' }
```

The inspector checks video metadata, audio presence/duration, chosen center pixels and optional full decode; it records the actual output SHA-256 and tools. Duration tolerance is max(2 frames, 100 ms), RGB tolerance is 12 per channel. No color assertions are appropriate after intentionally grading or covering the sampled pixel. This helper does not establish perceived audio quality, caption readability, lip sync, color management or UI usability. It refuses an existing evidence path; use new names for repeats. Inspect every expected stream/PNG separately where the helper does not cover it.
